# Edge function rules

- Onway webhook validates the shared query token, logs to service-role-only onway_webhook_log in the background and always acknowledges independently of processing, because provider retries must not depend on our failures.
- Manual Onway batch alerts fire once on store-B import_batches applying-to-finalized transitions with the authenticated actor; real API batches notify once after the send loop when attempts exist, using EdgeRuntime.waitUntil, so dry runs, duplicate locks and chunked uploads do not spam or change shipment results.
- Onway API shipments go through `onway-create-shipments` (admin-only, store B, same selection/label logic as export-courier) and always via `_shared/proxyFetch.ts`; orders are atomically claimed by setting `onway_sent_at` before calling api/order/add and that mark is never auto-cleared, because Onway's response format is undocumented and a failed-looking call may still have created a shipment.
- SMS goes only through Sender.ge via `supabase/functions/_shared/senderGe.ts` over `proxyFetch` (Sender.ge whitelists the static IPs; POST form body, 9-digit destination, retries only on 503/network); `sms_logs` failed or stale-pending rows are reclaimed atomically by `sms_claim_retry`, so retries never double-send.
- Customer SMS sequence: lead_created sends synchronously via `send-sms`; every later step is enqueued idempotently in `sms_queue` (order trigger or Onway webhook via `sms_enqueue`) and sent by the `sms-queue` worker, with templates/GSM-7 guard/delivery-date/quiet-hours in pure `_shared/smsTemplates.ts` (also imported by the admin preview), because one renderer must match what customers receive.
- Onway webhook actions come only from admin-mapped `onway_status_map` rows and orders matched by `onway_tracking`; unknown statuses default to `none`, so courier-import data or guessed statuses never trigger customer texts.
- Onway API sends finish through `_shared/onwayFulfill.ts` (label/zone/date, courier_export event, one import batch, `bulk_fulfill_orders` via the admin's own client) and export-courier excludes API-sent/unclear orders, because API-sent orders must reach Courier Labels and never ship twice via Excel.
- Courier shipment rows from every source (Excel import, Onway webhook, backfill) are built by pure helpers in `supabase/functions/_shared/courierShipment.ts`; API payloads write only through the `courier_upsert_shipment` RPC (newer `source_status_at` wins, finalized rows immutable except pickup-cancelled, which Onway can reopen by scanning later), because Excel and API must never compute or overwrite courier states differently.
- `onway-status-pull` handles admin/cron actions backfill (replay stored webhooks), silent_check (webhook-silent Telegram alert, cron Mon–Sat Tbilisi hours) and read-only probe; provider pull stays disabled until Onway documents a status endpoint, because guessed routes returned 404 or "no API permission".
